## Issues

### Critical

None found.

### Important

1. **[P1] Unrelated revocations fence valid clients across worlds.** `apps/server/internal/realtime/hub.go:231` compares a single global revision; `:329` increments it for every revoke regardless of world/user. If B is in an authorization query when A logs out or a member of world A is kicked, B's valid `Validate` returns `ErrFenced`; `apps/server/internal/realtime/connection.go:143` or `:157` then closes B with a policy error. Unrelated joins/resumes similarly fail at `hub.go:139`/`:189`. This violates revocation scope isolation and produces terminal access-denied UI for still-authorized users. Fence with relevant account/world/membership generations, or repeat authorization on a revision change before deciding the caller is unauthorized. Add a gated test that revokes A while B validates/joins, alongside the existing same-subject admission race test.

2. **[P1] Explicit leave races socket close and may retain the old seat.** `apps/web/src/net/socket.ts:97` sends `world.leave` and immediately closes the socket; `apps/server/internal/realtime/connection.go:115` queues the command, but `:131` returns immediately when the reader finishes, even when that command is queued. If the close frame is read before the writer services the queue, selection of `readDone` discards the leave. Deferred `Disconnect` then keeps the seat for 30 seconds instead of releasing it. `apps/web/src/online-ui.ts:18` also starts a replacement join without waiting for release, so a normal world switch/rejoin can be reported as control held by another tab, and other members retain an AFK avatar after an explicit return to solo. Make deliberate leave an acknowledged operation, sequence replacement joins after it, and ensure transport close does not discard an already-received leave. Add deterministic leave-plus-close and leave-then-other-world tests; the current socket test checks only local status.

3. **[P2] Admission errors can orphan live reservations or uncounted avatars.** `apps/server/internal/realtime/hub.go:157` removes/stops the old seat before fallible runtime work; `:176` publishes a new seat before the fallible snapshot. Resume similarly rotates/publishes at `:192`–`:198` before `Join`/snapshot. A context canceled while waiting for the hub lock (after authorization) makes `Runtime.call` reject the subsequent work; cancellation after runtime join can make the final snapshot fail. There is no rollback. A failed resume can leave a new active seat with `disconnected` zero and an opaque ID the caller never received; it never reaches 30-second expiry. A failed same-world takeover can leave the old runtime avatar after its seat was deleted. The handler installs its cleanup only after success (`apps/server/internal/realtime/connection.go:54`–`:69`), so it cannot repair these errors. Make admission/rotation transactional or guarantee cleanup on every post-mutation failure, preserving bounded reservations and avatar/seat consistency. Add cancellation gates before runtime join and before snapshot, checking that failures leave no permanent seat/ghost avatar.

4. **[P2] Main exits before graceful HTTP shutdown finishes.** `apps/server/cmd/server/main.go:56` runs `server.Shutdown` in a goroutine, while `:63` resumes as soon as Shutdown closes the listener and `:67` returns from main. The five-second Shutdown drain is therefore not awaited; active REST handlers can be terminated and the pool closed while they are running. Await shutdown completion before main exits, and handle/report its error. A focused signal/shutdown test with one blocked handler should assert the process waits for the handler or the timeout.
