## Important findings

### R1 — Reopening a guest race silently disables controls until a fresh counter catches up

**Locations:** `apps/web/src/features/race/Race.tsx:38–41`, `apps/web/src/features/race/session.ts:6–9`, `apps/web/src/features/race/local.ts:20`.

`RaceGame` owns `seq=useRef(0)`, but the singleton guest session and its kart's accepted sequence survive modal unmount. Every mounted 50 ms update increments that ref, including neutral input. Reopening creates a new counter starting at zero while `LocalRace.input` rejects every `seq <= k.seq`. The UI ignores those false returns. A previously open panel with 600 updates therefore rejects approximately the next 30 seconds of controls. The race and bots continue during that interval, so preserving its visual identity alone is insufficient.

**Confirmed:** a focused execution of the real guest session accepted sequence 600, then rejected reopened sequence 1, and accepted 601. The coordinator independently reported actual unchanged-build CUA evidence: reopen at 52.46 seconds, hold W for two seconds, Guest remains at `(18432,5600)` through 54.66 seconds; much later controls recover and move the kart. Root's evidence image is `docs/checkpoints/evidence/CP5/t10-guest-reopen-input-failure.jpg`. The earlier continuation smoke did not attempt driving after reopening and does not contradict this finding.

**Fix:** keep guest input sequencing with the persistent guest session, or explicitly restore a valid controller sequence when attaching the panel. Preserve monotonic rejection rather than removing it from the simulator.

**Required regression:** accumulate a large sequence during a running guest race, unmount and remount the controller, then require the first new throttle/steering input to be accepted and to move/turn the same kart immediately. Assert unchanged match identity, progress and deadline. The present session test only checks identity/deadline and never sends a remounted controller input (`apps/web/tests/race.test.ts:12`); the authored E2E also does not drive after reopening (`race.guest.e2e.spec.ts:3`).

### R2 — Race advances during the owner's unordered disconnect-metadata pass

**Changed location:** `apps/server/internal/games/race/engine.go:274–299`, especially `:278`. **Actual integration:** `apps/server/internal/lobby/presence.go:27–44`, `:391–415`.

The owner intentionally installs every pending disconnect before performing catch-up or evaluating a terminal boundary. It calls `recordDisconnect` while iterating the pending map, then sorts notifications. Race's new `Presence` calls `Tick(at)` before installing the disconnect, so that supposedly metadata-only pass now advances physics in random map order. If B's later timestamp is processed first, A is simulated without A's earlier disconnect/takeover; applying A afterward cannot rewind the engine. The unchanged penalty disconnect branch explicitly installs metadata and returns without ticking (`apps/server/internal/games/penalty/engine.go:191–200`).

**Confirmed:** one focused overlay test fed the two valid installation orders for the same timestamped batch: A disconnect at 4000, B at 5000, followed by Tick(5000). Chronological installation leaves A at `(18608,5634)`; reverse map iteration leaves A at `(18432,5600)`, both at frame 30. Thus authoritative motion depends on map iteration, and delayed batches can use the wrong controller before grace/result evaluation. This is a new race integration defect, distinct from prior O1's processed disconnect/coalesced resume/new-disconnect defect.

**Fix:** honor the owner's batch installation contract: no simulation or finalization while installing unordered disconnect metadata. Apply takeover and grace using original timestamps when the subsequent ordered advance occurs; retain natural finish precedence at the exact deadline, neutral input, immutable actor/assistance history, and bounded catch-up. Do not merely restamp arrivals or broaden generic O1 scope without need.

**Required regression:** use the actual lobby plus race adapter with the owner held while multiple differently timestamped disconnects accumulate. Prove equivalent motion/takeover regardless of pending-map installation order, then cover delayed ingestion spanning an original 15-second grace, all-human abandonment, and natural finish at the same/later deadline. Retain the accepted activation replay cases and verify terminal events remain published. The existing direct-engine and simultaneous-deadline tests do not exercise this unordered registration phase.
